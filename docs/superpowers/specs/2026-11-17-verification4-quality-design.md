# Recheck 검증4 후속 수정과 전체 코드 감사 설계

0.1.5 작업 당시의 설계다. 실제 수정과 최종 검증은 [코드 감사 보고서](../../PROJECT_AUDIT_REPORT.md)를 따르며, 이후 버전 전체의 현재 상태를 설명하는 문서는 아니다.

사용자 요청: 검증4 자료 전체를 읽고 검증3의 유효한 근거를 대조하여 기능을 수정하고, 루트의 코드 감사 지시서에 따라 실제 개선·검증을 수행한다. 마지막으로 기존 GitHub 양식에 맞춰 새 Windows prerelease를 배포한다. 기존 사용자 파일과 인증·분석 데이터는 보존한다.

## 접근 방식과 결정

기존 Python/PySide6와 제한된 ZIP STORED/DEFLATE 계약을 유지하고, 재현 가능한 결함을 먼저 고친다. ZIP 지원 형식을 확대하거나 외부 검증 서비스에 전면 의존하면 지금 필요한 무결성 보완보다 호환성과 배포 부담이 커진다. 따라서 기존 스트림을 독립 검증하고 모순되거나 지원하지 않는 조합을 명시 거부한다.

보고서 경계는 과거 JSON의 누락·null·잘못된 타입을 안전하게 표현하고 원본을 수정하지 않는다. 분석 시작 이전 차단은 run을 만들지 않는 공통 preflight로 일치시키며, 시작 이후 실패는 현재 이력·실패 보고서 계약을 유지한다. 자동 준비는 선택한 adapter에 필요한 환경만 준비하고 명시하지 않은 준비를 수행하지 않는다. 도구 진단은 실제 실행과 동일한 탐색 결과를 사용한다.

검증3은 과거 버전의 재현·회귀 근거로 사용하고, 검증4에서 해결이 확인된 문제를 다시 미해결로 취급하지 않는다. 기존 재검사·확인 범위·실패 HTML/JSON 계약을 회귀한다. TokenEconomizer 설정 변경, 사용자 전역 Docker MCP 변경, 유료 모델/새 계정, 새 외부 MCP 제품 기능은 이번 결함 수정에 필수적이지 않으므로 도입하지 않는다.

## 수용 조건

- PKG01 네 조작 fixture와 source/CLI의 다섯 실패 관찰이 success/equal로 나오지 않는다. 정상 ZIP, descriptor, 빈 파일, 경로·취소·상한 회귀를 유지한다.
- 보존된 Server=null JSON은 같은 해시 상태에서 source/frozen 보고서를 생성한다. 미기록·null·실패는 정상 관측으로 추정하지 않는다.
- 분석 전 형식/모드 차단은 CLI와 GUI에서 이력을 생성하지 않고 안전한 사유를 제공한다. 실행 시도 실패 이력은 유지한다.
- direct/managed 선택에 맞는 준비만 수행한다. Java/Ollama 진단과 실제 사용 경로가 일치한다.
- 유지보수 소스·테스트·빌드·CI·설정·문서의 검사 범위와 제외 항목을 기록한다. SonarQube/CodeQL/OSV/Scorecard/Ruff 적용 가능성과 실제 결과를 구분한다.
- 전체 Python/Node 검사, 관련 정적 검사, frozen CLI, 실제 GUI, 가능한 실제 Docker 비교를 통과한 새 빌드만 게시한다. 미실측 Windows VM/PE/AI는 성공으로 주장하지 않는다.
- 새 버전·브랜치·PR·정확한 SHA CI·새 draft prerelease·ZIP 해시/크기 대조·최종 페이지 확인 절차를 따른다. 과거 태그/자산은 덮어쓰지 않는다.

## 위험과 제한

ZIP 독립 검증은 자원 상한과 취소를 동일하게 적용해야 한다. 과거 기록 스키마를 일반적으로 재작성하지 않는다. 패키지 업데이트는 실제 취약점·지원 근거가 있는 호환 업데이트만 적용한다. 공개 보고서는 집계와 재현 방법만 포함하고 개인 경로·원시 분석·인증 자료를 배포하지 않는다.
