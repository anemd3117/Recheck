# 앱 내부 AI 연결과 Windows 배포 설계

상태: 구현 요구사항 · 2026-11-17

## 목표와 범위

사용자는 기존 내장 로그인 시제품을 Recheck에 통합해 배포 가능한 품질로 만들고, 잘 동작하면 배포하도록 요청했다. 앞서 검토한 [공통 제공자 설계](../../decisions/0004-provider-onboarding.md)를 구체화한다. 같은 브랜치에서 구현·검증하고, 실제 확인한 범위만 Windows 미리보기 배포에 포함한다. 별도 로그인 시제품만 실행되는 ZIP을 제품 EXE로 설명하지 않는다.

GPT/ChatGPT·Gemini·Grok·DeepSeek·Claude의 공통 연결 안내, 공식 키 콘솔 표시, API 키 보안 저장·실제 응답 검사, ChatGPT OAuth의 선택 가능한 내장 표시를 다룬다. Google Desktop OAuth와 연동 Google 인증은 정책상 내장 경로를 제품 기본값으로 제공하지 않는다. 원격 사이트의 지원 계약을 앱 코드로 보장하거나 차단을 우회하지 않는다.

## 사용자 화면

```
AI 연결
[ChatGPT 로그인] [Gemini] [OpenAI API] [Grok] [DeepSeek] [Claude]
연결 방식 · 사용량/근거 전송 안내 · 공식 사이트 안내
[앱에서 로그인/키 발급 화면 열기] [다른 방법으로 연결]
로그인 대기 → 승인 확인 → 응답 검사 → 연결 완료

공식 연결 창
표시 중인 사이트: https://공식호스트
[공식 웹 화면]
상태·실패 안내 · [기본 브라우저에서 계속] [연결 중단]
```

인증서·페이지·렌더러 오류와 제공자 제한은 이해할 수 있는 고정 문구로 표시한다. 외부 브라우저는 사용자가 선택했을 때만 연다. 콘솔 연결은 사용자가 직접 키를 발급하고 가려진 네이티브 입력란에 입력한다. 결제·유료 업그레이드·키 생성 자동 클릭·DOM 키 추출은 수행하지 않는다.

## 결정과 대안

- 공통 네이티브 안내와 WebEngine 창을 채택한다. 기존 프로필·DPAPI·응답 검사·현재 선택 보호를 재사용한다.
- 후속 사용자 요청에 따라 로그인·키 발급은 시스템 브라우저를 기본으로 하고, 모든 제공자의 내장 선택을 기본 해제로 유지한다.
- 모든 제공자에 동일한 내장 OAuth를 강제하지 않는다. Google은 정책 제한, ChatGPT는 공식 시스템 브라우저 안내와 내장 호환 경로를 구분한다.
- 배포는 기존 onedir ZIP을 유지한다. WebEngine의 정확한 DLL·리소스·고지·대응 소스를 포함하고 기존 출처 검증을 확장한다.

## 인증과 스레드 경계

`OAuthService.login(..., on_url=None, *, on_event=None)`, `ProfileManager.login(..., *, on_url=None)`와 `ChatGPTSetup.connect(..., on_url=None)`로 표시 담당자를 주입한다. 지정한 표시 담당자가 실패해도 시스템 브라우저로 자동 재시도하지 않는다.

전체 인증 URL은 worker에서 UI로 가는 전용 queued signal로만 전달한다. 공개 progress/event 경로에는 URL·쿼리·계정 식별정보·원시 예외를 넣지 않는다. 기존 로그가 event 전체를 기록하므로 이 경계를 유지해야 한다.

콜백 검증 이벤트는 기존 loopback 검증을 통과한 결과를 받았을 때만 보낸다. 토큰 교환·서명 확인·프로필 commit·실제 응답 성공을 서로 구분한다. 페이지 이동이나 loadFinished로 승인·로그인 성공을 판정하지 않는다. 저장 후 관측 이벤트 실패 때문에 자격증명 참조를 잃지 않도록 한다.

각 연결에 고유 attempt ID를 둔다. 취소·완료·프로필 변경 뒤 도착한 URL과 진행 이벤트는 무시한다. 창 닫기·메인 취소·완료·실패 모두 팝업·페이지·프로필 수명을 정리한다. 브라우저 종료와 작업 스레드 종료 순서를 보장한다.

## 브라우저와 자료 보호

연결마다 새로운 off-the-record 프로필을 사용한다. 시스템 브라우저 쿠키를 가져오거나 브라우저 세션을 Git·ZIP·설정에 저장하지 않는다. OAuth 토큰과 사용자 키는 기존 Windows 사용자 DPAPI로 보호한다.

같은 연결 작업 안에서 코드 교환 거절 후 새 승인이 필요한 경우에는 메모리의 동일 웹 프로필을 유지한다. 이전 페이지·팝업·이벤트 담당자는 정리하고 새 페이지와 고유 이벤트 세대, 새 정확한 callback 허용 목록으로 교체한다. 새 state·nonce·PKCE·코드와 전체 제한 시간은 기존 인증 서비스가 관리한다. 다른 연결 작업·취소·실패·완료·외부 전환에서는 이 임시 프로필도 파기한다. 이 수명 조정은 재승인 때 불필요한 웹 로그인을 줄이며, 서버의 인증 거절이나 계정 사용 권한 자체를 해결한 것으로 보지 않는다.

콜백 페이지는 승인 결과 수신만 안내하고 Recheck의 인증 저장·최종 결과 확인을 구분한다. 재승인 안내는 첫 로그인 화면의 일반 안내로 덮어쓰지 않으며, 네이티브 진행 상태는 승인 확인 단계에 머문다.

HTTPS와 정리용 about:blank만 허용하며, HTTP는 실제 생성한 `127.0.0.1:<port>/auth/callback`에만 허용한다. URL의 userinfo·잘못된 포트·중복 redirect_uri·로컬 파일·임의 scheme을 거부한다. Google 내장 인증 이동은 제한 이유와 사용자가 선택할 외부 경로를 제공한다. 인증서 검증·Chromium sandbox·웹 보안을 끄거나 UA를 위장하지 않는다. 다운로드·불필요한 장치 권한을 차단하고 상태에는 origin만 표시한다.

## API 키 연결

제공자별 공식 URL과 고정 endpoint를 가진 데이터 목록을 사용한다. Grok·DeepSeek는 기존 compatible 어댑터를 사용하되 해당 서비스의 기능 지원은 실제 검사 결과로 표시한다. API 키 저장만으로 연결 완료나 무료 등급을 표시하지 않는다.

기존 Gemini 무료 확인·근거 전송 동의는 보존한다. 다른 키 제공자는 명시적 근거 전송 동의 후 모델 조회·기본/구조화 응답·검사 기록 저장을 수행한다. 확인한 프로필과 기존 선택이 바뀌었으면 기본 AI를 덮어쓰지 않는다.

## 검증과 배포 판단

- 자동 검사: URL 경계, 위조 콜백/서명, 진행 순서, UI thread 전달, 뒤늦은 신호, 취소·실패·팝업·종료, 키/토큰 비노출, 실제 응답 proof 없이 선택 방지.
- 일반 단위 검사는 실제 웹 네트워크·WebEngine 프로세스 없이 수행한다. 별도 실제 UI 검사에서 WebEngine 표시와 조작을 확인한다.
- 제품 소스 전체 pytest·Node 정규화·Ruff·의존성 검사와 GitHub 해당 SHA의 단위·보안 검사를 통과한다.
- frozen EXE에서 WebEngineProcess·DLL·locale·pak·고지·대응 소스 구성과 정상 실행을 확인한다. 소스 창 표시를 EXE 검증으로 대체하지 않는다.
- 실제 계정 인증·응답은 사용자가 직접 진행한다. 인증 완료를 확인하지 못하면 이를 지원 완료로 표시하거나 조건부 배포를 완료했다고 보고하지 않는다.
- 성공한 범위와 남은 제약, 제공자별 검증 상태, 설치·복구 절차를 기록한다. 기존 릴리스 자산은 덮어쓰지 않는다.
